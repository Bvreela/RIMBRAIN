# Steward submodule build specification

**Status:** READY  
**Future path:** `components/steward`  
**Future remote:** `rimbrainagent-steward`  
**Base:** extract upstream `mod-steward/`

## 1. Purpose

Steward is the deterministic RimWorld add-on that performs high-frequency work-priority, stock, research, and standing-order behavior without model latency. It is agent-specific policy implemented close to the game and loaded after generic RimBridge.

## 2. Existing baseline

The upstream add-on already provides:

- managed-pawn work-priority scoring;
- stock jobs for forestry, forage, hunting, mining, production, and livestock;
- time-boxed posture adjustments;
- ordered research queue;
- standing orders for combat, rescue, unforbid, corpses, beds, policies, blueprints, and fire;
- manual-touch cooldown/ownership behavior;
- `steward.*` RPCs and ledger events;
- save/load persistence and pure-logic xUnit tests.

These behaviors should be extracted with history/attribution where practical, not rewritten first.

## 3. New responsibilities

- Publish capability/version information and contract-compatible RPC examples.
- Accept desired-state commands with caller intent/idempotency metadata where relevant.
- Return ownership/effect identifiers sufficient for runtime verification.
- Emit structured state-change/reflex events with stable reason codes and correlation metadata when supplied.
- Expose deterministic emergency/vitals observations only when they are game-close, generic enough for Steward, and cheaper/more reliable than Python polling.
- Enforce posture/safety permissions that must survive runtime latency.
- Provide safe-pause request capability through RimBridge if generic bridge support exists.

## 4. Non-goals

- Strategic planning or model calls.
- RimBrain pack loading.
- Cross-episode learning.
- Generic reflection engine changes.
- Owning the Python framework dispatcher.
- Arbitrary policy execution from network data.

Names/package IDs require a release ADR to decide compatibility versus side-by-side install. Initial migration should preserve upstream package identity unless conflict evidence requires renaming.

## 6. RPC evolution

Keep existing `steward.*` behavior compatible. Add a capabilities method that reports component version, contract version, supported commands/events, save schema, and optional features. New desired-state calls accept optional metadata:

- `intent_id`;
- `idempotency_key`;
- `owner`/policy revision;
- `expected_previous_revision`;
- expiry or bounded duration.

Repeated idempotency keys return the known effect/result rather than duplicate work where persistence permits. Existing manual dashboard/legacy calls remain supported but are labeled uncorrelated.

## 7. Ownership model

Steward owns only objects/actions it creates under its managed scopes. It reports owned designations, bills, rally assignments, queue entries, posture, and standing-order touches. Manual player/runtime changes suspend matching ownership according to explicit cooldown or release rules. Runtime dispatch composes one desired Steward state rather than issuing competing domain writes.

## 8. Emergency behavior

Standing orders remain deterministic. Safety additions are accepted only when all required data is available synchronously, action is bounded and reversible enough, and behavior is configurable/testable without a model. Runtime hard invariants still validate strategic intents; Steward provides the final low-latency reflex layer.

Potential phase-gated additions:

- treatment/rescue latency ledger details;
- pawn life-critical transition events;
- safe shelter-in-place order;
- critical-role protection input generated by runtime policy;
- dead-man safe pause hook.

Each requires a separate feature spec and pure-logic fixture before live inclusion.

## 9. RimBridge dependency

Build against the exact direct `integrations/rimbridge` submodule. Use only public `Rpc.RegisterAssembly` and `Hooks` extension points where possible. Generic missing capability changes are proposed upstream to RimBridge, not embedded as Steward hacks.

## 10. Extraction plan

1. Create standalone repository preserving MIT and third-party notices.
2. Copy/extract `mod-steward` with tests and build metadata.
3. Replace relative nested-mod DLL path with configurable superproject integration path/package artifact.
4. Establish contract fixtures for all 18 existing RPCs before changing them.
5. Add capabilities/version endpoint.
6. Add optional correlation/idempotency fields compatibly.
7. Add structured ledger event versions.
8. Update runtime gateway after old/new contract compatibility tests pass.

## 11. Tests

- Preserve existing threshold, plant math, rule, and order tests.
- Add contract golden tests for every RPC and event.
- Add save/load migration tests for managed state and idempotency cache.
- Add manual-touch/ownership race tests.
- Add duplicate desired-state and repeated-intent tests.
- Add bounded-time/per-tick performance budgets.
- Add integration tests against pinned RimBridge assembly.
- Add multiplayer/multi-map behavior only if later supported; otherwise explicitly reject unsupported scope.

## 12. Acceptance

- Existing functionality remains compatible with legacy upstream client.
- Framework runtime can discover exact capabilities/version.
- Every framework-originated Steward mutation is correlated to a dispatcher intent.
- Duplicate intents do not duplicate effects in covered operations.
- Standing orders remain model-independent and pass performance/safety budgets.
- No generic RimBridge policy coupling is introduced.
