Research & implementation specification

A reviewable AI framework for planning and playing RimWorld

Prepared for Ben · Revision 7 · Pawn-aware building strategy and persistent lessons · Two interchangeable agent API roles · Domain order: food → shelter → mood → research → combat. Specification only; not implemented or tested in game.

The framework plans, selects current goals, breaks those goals into tasks, and cycles attention across the work. Each attention turn uses a small decision matrix to choose a permitted game action. Two independently configurable API roles provide planning and action selection. Humans can inspect the plan, task logic, matrix, and observed results; failure analysis proposes improvements to each layer.

Provider independence: configure a Planner endpoint and a Decision Selector endpoint. Claude and Jev are optional provider adapters, not required dependencies. Compatible endpoints can be swapped in settings; a different API protocol needs an adapter. Each selected endpoint must satisfy its role’s capability contract.

Learning: initially change the surrounding policy: state features, question wording, examples, decision thresholds, action templates, and eventually a separate trained selector. Provider weight training is optional and separate. If Jev is selected, TypeSafe explicitly says customer fine-tuning and LoRA adaptation are unavailable. [4]

Recommended first milestone: the complete plan → goal → task → attention → decision matrix → action → verification loop for food management, with a readable review screen and one failure-to-improvement example. Start in shadow mode, then compare it with the same framework using deterministic decisions.

Requested rollout: food → shelter → mood → research → combat. The first colony-management release covers food, shelter, and mood; research follows, then combat. Each domain uses the same inspectable task, matrix, verification, and learning contracts.

Responsibilities

  • Planner endpoint: translate human objectives and current evidence into a structured plan, select current goals, and propose tasks from an approved capability catalog. Replan on a changed objective, an invalidated assumption, an infeasible goal, or repeated failure. The same endpoint handles reflection through a separate bounded request type.
  • Goal/task manager: validate dependencies, resources, measurable completion conditions, and supported capabilities. Persist progress and blockers across attention turns. A planner cannot declare work complete without matching observations.
  • Attention cycler: decide which task or monitoring obligation to inspect next using explicit priority, urgency, deadline, readiness, and time-since-review rules. It can observe, verify, unblock, or request replanning without issuing a game action.
  • Decision Selector endpoint: select a bounded next action for the focused task using its matrix. This can be Jev, a general model, or a custom agent that satisfies the selection contract. If there is no judgment to make, execute a deterministic check or rule and record that route. The selector role has no authority to rewrite the strategic plan.
  • Steward and execution code: enforce emergency overrides, work priorities, stock maintenance, legal action filtering, arithmetic, bounded parameters, timers, and verification. Existing automation still needs scenario tests; “deterministic” does not mean invulnerable.
  • Reflection using the Planner endpoint: diagnose failures, curate examples, and propose changes to planning templates, task decomposition, attention rules, or matrices. No third model endpoint is required. The default action fallback is deterministic rules; new executable capabilities require their own validation.
  • Experiment runner: control versions, save files, independent episode state, seed cohorts, metrics, and promotion. Neither endpoint can modify the evaluator, hard constraints, or final test set.

Framework boundary: keep plan/goal/task storage, attention scheduling, matrix evaluation, review, and promotion in the core. Put RimWorld observations, game predicates, task/action templates, and RPC mappings in a RimWorld adapter. Begin with one local process and a durable store; a distributed agent system is unnecessary for the first implementation.

Ownership matters: Steward postures replace one another; two independent domain choices must not both call steward.posture and silently overwrite each other. The arbiter selects one combined posture and serializes changes. Avoid duplicate Python watchers for enabled Steward orders: manual touches can temporarily suppress the very standing orders they duplicate. [2]

Lifecycle: proposed → ready → running → awaiting_result → succeeded. Tasks may become blocked, suspended, failed, or cancelled with explicit reasons. A blocked task becomes ready only after its blocker is observed resolved; a suspended task reconciles live state before resuming. Bounded retries create recorded attempts. Dependencies unlock on verified success, never on “RPC returned OK.”

Goal lifecycle: proposed → current → satisfied or failed; current goals can be suspended or cancelled with a reason. An achievement goal completes once its predicate is verified. A maintenance goal remains monitored: falling below its target creates recovery work instead of being forgotten. The current-goal limit is an initial three ordinary goals; emergencies can preempt this limit. Goals and numbers are operator-visible policy settings, not fixed universal strategy.

Decomposition contract: tasks form a directed acyclic dependency graph. Reject cycles, unavailable capabilities, unbounded tasks, conflicting reservations, and missing success tests before activation. If a task needs an unknown capability, create a visible capability gap and request replanning; do not invent a tool. The generative planner produces structured data referencing approved predicates and templates, never executable condition strings.

Plan once at episode start, review roughly once per game day initially, and replan on meaningful changes. Task progress updates continuously. Stable completed work survives a plan revision; removed work is explicitly cancelled and owned reservations/designations are reconciled. Late model replies for superseded tasks or endpoint configurations are discarded. Adaptive planning within an episode changes the current plan; reusable policy learning changes how future plans are made, through the promotion process.

2B. Attention cycling is a scheduler with memory

The cycler manages attention across goals; it does not blindly rotate through domains or repeatedly ask a model “what now?”. Task state, event subscriptions, and next-review times determine what is eligible. All choices below must be visible in the review UI.

  1. Ingest and reconcile: consume new game events, refresh stale required facts, verify pending outcomes, resolve observed blockers, and discover deadline or maintenance breaches.
  2. Apply overrides: operator pause blocks new writes; deterministic emergency responses preempt ordinary work. The interruption records the affected task, its already-executed steps, and the condition for reconsidering it.
  3. Form the attention queue: include runnable tasks, due verification checks, due blocked-task inspections, and maintenance goals needing review. A task waiting on work has a scheduled check, not permission to reissue the same order every turn.
  4. Select visibly: after emergencies, service overdue critical deadlines and maximum-review-interval obligations. Rank remaining eligible items with the published scoring rule. Break ties by oldest attention time, then stable task ID.
  5. Take one bounded turn: observe/verify if that is the work due; otherwise build the focused task’s legal candidate set and ask the configured selector to evaluate its matrix. Start with one matrix decision and one action template per turn, each with bounded RPC count and time.
  6. Persist and yield: record results, update task state, release or retain reservations explicitly, set the next review time, and return to the queue. An interrupt checks again before each write; uncertain outcomes are reconciled before retry.
Illustrative normal-task attention score; all inputs in [0, 1]:
  4 × urgency
+ 3 × current_goal_priority
+ 2 × time_since_review
+ 1 × readiness
− 1 × switching_cost

Hard precedence: emergency → critical deadline → overdue review → score.
Tie break: oldest attention timestamp → stable task ID.
Blocked/awaiting tasks enter only for a due inspection or new event.
If nothing is due, sleep until the next event or review deadline.

These weights are starting hypotheses. Compute each factor and its evidence in code, display the contribution, and version changes. Set maximum review intervals per task type to prevent starvation; report missed review obligations when emergencies or overload make the schedule infeasible. Do not promise fairness by simply adding a small age bonus.

Keep a minimum focus dwell/cooldown to reduce oscillation, but allow emergency and deadline preemption. Only one dispatcher owns game writes. Multiple tasks can await game progress simultaneously without issuing conflicting commands. On restart, rebuild the queue from persisted state and reconcile outstanding actions against the game before resuming.

2C. Human review is a core part of the framework

One source of truth: store plans, research priorities, task templates, scheduling rules, and matrix definitions as versioned, schema-validated YAML or JSON. Generate the readable tables and live UI from those same definitions. Structured UI edits produce a proposed diff in that source; do not maintain a separate spreadsheet that can drift from executed logic. Conditions use a small catalog of typed predicates, not arbitrary code.

Review modes: shadow mode records proposed actions; supervised mode lets a human approve selected action classes or plan revisions; autonomous mode runs the accepted policy and permits only explicitly configured classes of tested improvements. Easy review does not require a human to approve every model call. Configure these modes per experiment and show the active mode prominently.

Normal policy and endpoint edits are staged, checked, and activated at a clear boundary. An immediate operator override is recorded with its author and effect; it may change the live plan, but the resulting run is labeled as assisted for comparisons. Emergency pause remains directly available. Display policy, plan, matrix, adapter, and endpoint/model versions on every trace.

Acceptance test for readability: using only the review interface, a person must be able to answer: “What are we trying to achieve?”, “Why this task now?”, “What else could the selector choose?”, “What did we actually do?”, “Did it work?”, and “What would this proposed improvement change?” An exported report must preserve that same trail. Explanations expose stored inputs, rules, scores, and evidence; they do not pretend to reveal a model’s internal reasoning.

2D. Example settings registry and agent-created proposals

The companion settings/ directory now contains an example for every planned human-editable input: endpoint roles, objectives, task templates, attention rules, all domain matrices, Planner and reviewer guidance, evaluation, research priorities, long-term plans, action workflows, building strategy, and lessons policy. registry.example.yaml gives every settings input a kind, stable ID, revision, owner, and load position. The separate lesson-records.example.yaml illustrates stored evidence records and is not active configuration. The examples are review artifacts; RimAgent does not load them yet.

Long-term planning: a plan stores its horizon, strategy, assumptions, constraints, milestones, dependencies, workflow references, replan triggers, and measurable completion condition. Only the next actionable goals and ready workflow nodes enter the attention queue. This preserves a long horizon without asking a provider to regenerate the entire plan every turn.

Action workflows: a workflow is a directed acyclic graph of observation, bounded task-template, wait, and verification nodes. Ready task nodes are scheduled through the same attention cycler and dispatcher as ordinary tasks; a workflow cannot contain raw RPC calls or bypass matrix, resource, and verification rules.

Adding more settings: settings-generation.example.yaml defines a proposed propose_settings_package application tool. The Planner can create new instances of allowlisted objectives, task templates, matrices, long-term plans, and workflows only under a proposal workspace. The tool validates schemas, IDs, paths, references, workflow cycles, matrix bounds, budgets, and declared fixtures, then renders a package diff. Proposal creation never changes the active registry. Activation is a separate atomic transaction with full revalidation, provenance, a trial result, and a rollback revision. New schemas, provider secrets, predicates, or game actions still require code and human review.

The sample package under settings/proposals/winter-readiness/ demonstrates a complex goal that adds an objective, task template, decision matrix, long-term plan, and workflow as one reviewable proposal. It is not active configuration and contains no claim that the winter strategy has passed gameplay trials.

3. A small, hierarchical decision matrix

Attach each matrix to a task template. The attention cycler selects the task; its matrix selects a permitted next action. A matrix row offers at most four productive options, plus CONTINUE and ESCALATE. CONTINUE preserves valid in-progress work and sets a review deadline. ESCALATE requests missing observations or replanning; after a bounded attempt it falls back to rules or pauses on an unresolved emergency. Neither option means waiting indefinitely.

Do not offer every strategy at once. Generate candidates from actual targets and unlocks, attach resource and time estimates, remove illegal candidates, and then ask the configured selector. A crop ID, project ID, or location always comes from the game or a validated planner—never from invented text.

Skill-aware building strategy and map adaptation

Policy input: building-strategy.example.yaml makes pawn capability part of shelter planning. Low available mining capacity favors reuse or open construction when those choices are feasible. Skilled, healthy, available miners increase the attractiveness of excavated space when the full project can meet its deadline. Compare construction capacity too: excavation still needs debris clearance, doors, furnishings, and temperature control. A high-level miner who is injured, drafted, or the only available cook contributes only their genuinely unreserved work time. Passions inform training potential, not an invented current work-rate bonus.

Compare total work and future utility. Deterministic estimates combine effective rates, available hours, travel, hauling, interruptions, and the number of reachable work faces. Show uncertainty and the critical path; do not simply sum every pawn's skill level or apply an arbitrary mining-level cutoff. Keep the immediate shelter deadline ahead of long-term optimization, and compare later benefits over the plan horizon. Secure usable floor area, controlled approaches, lower structural flammability, suitable temperature, and expansion capacity are benefits; labor, materials, displaced food/medical work, and hazards are costs. “More valuable” means better service to colony goals, not greater game-market wealth.

Security and fire resistance are conditional. Rock barriers can reduce ordinary attack approaches and rock/stone walls can be less flammable than wooden walls. Validate actual terrain and material definitions for the installed game. A room still needs safe colonist access and rescue/escape routes; breachers and internal threats can invalidate its defense advantage. Overhead mountain adds roof and infestation considerations, while flammable doors, furniture, and stored goods can leave substantial fire risk. Retain these as explicit candidate tradeoffs and evaluate them; do not label every mountain room superior or fireproof.

Existing controls versus new planning: RimBridge provides map/room observations, map.open_rects, ui.designate mining, and ui.build/ui.build_many placement. The open-rectangle helper samples currently open ground; it neither searches all possible layouts nor plans excavation. state.pawn supplies skills, capacities, disabled work, and assignments, but a complete throughput estimate needs further adapter work. The new spatial planner generates rotated, resized, irregular, and staged footprints; the selector receives at most four productive option IDs bound to validated candidate IDs, with estimates and rejection reasons. Unknown fogged space remains unknown until revealed. [11] [19]

Observe map + pawn capacity + applicable lessons
  → generate reuse / open / excavated / hybrid candidates
  → validate deadline, roof, access, materials, and survival labor
  → select and reserve one site plan
  → clear or mine one bounded phase
  → inspect new space and update completion estimates
  → construct and furnish ready areas
  → verify enclosure, access, temperature, and actual use
  → record outcome and propose a scoped lesson

The site plan persists its phase graph and cursor. Each phase returns through attention, bounded selection, dispatch, and observed verification; phase completion advances the cursor without making the workflow DAG cyclic. Do not place later blueprints behind unmined rock: Steward can cancel persistently unreachable blueprints. Reconcile work ownership before any manual pawn override, which also affects automatic combat drafting. Replan on worker loss, changed effective rates, newly revealed hazards, or missed deadlines. Cancelling a policy cannot restore excavated rock or spent time. [19]

A hybrid choice scopes the current site plan to temporary shelter, including sleep assignments and observed usability. Only after that goal and maintenance gates pass can a separate later upgrade goal become active. This prevents a multi-day excavation dependency from delaying tonight's sleeping space. If the overall shelter goal already holds, verify it and skip unnecessary tasks.

Matrix row contract

A row must be an executable specification, not a paragraph of advice. This is a proposed application schema, not an existing RimAgent configuration:

Store the exact decision question and option criteria, source/evidence links, resource budget, per-action timeout, stop condition, ownership of created designations, and measured acceptance threshold alongside each template. Matrix conditions determine eligibility; the configured selector then chooses among the offered options. Keep that distinction visible so a reviewer can tell whether the rules excluded an option or the model declined it. Resolve overlapping row matches by explicit priority or reject the ambiguity during validation.

The inspector’s table should show row → when it applies → allowed options → rejected options/reasons → execution mapping → verification → fallback. Click a row to view its provider-neutral instructions, adapter-rendered request, examples, and change history. A replay uses the saved observation, versions, and captured answer to reproduce the controller’s dispatch decision; it cannot reproduce alternate game outcomes. Calling a different endpoint or model is a new experiment, not an exact replay.

Some effects cannot be undone: eaten ingredients, elapsed time, and deaths are not recoverable by restoring a policy. Save reloads are permitted for explicitly labeled experiments, never as hidden recovery in scored episodes.

Turning priorities into the next project

  1. Resolve the real research catalog. Read current/finished/available projects and benches from state.research. Its available list is not a complete prerequisite graph; use validated definition extraction for locked projects, prerequisites, costs, and required facilities. Missing graph data blocks the affected goal visibly. Detect cycles, deduplicate shared prerequisites, and omit completed projects. [11]
  2. Apply human controls first. Excluded projects are never offered; a goal requiring an excluded prerequisite is blocked. A pinned next project outranks ordinary tiers but still needs its permitted prerequisites and legal start conditions. Show that chain and request review if a pin conflicts with an exclusion. Human pins and exclusions cannot be changed by an AI proposal without human approval.
  3. Check maintenance and capacity. Start only when the configured food, shelter, and mood maintenance checks pass, no emergency is active, the bench is usable, and research can use unreserved labor/materials. Reserve those resources through the shared task manager. Unknown checks defer research; there is no automatic sacrifice of the only cook or medic.
  4. Offer a small eligible set. Choose up to four candidates from the highest-priority tier that can advance. Order preferred projects within that tier, then use visible estimated effort and project ID as tie-breakers. If all higher-tier goals are blocked, explain the block before considering a lower tier; a blocked explicit pin waits for review instead. CONTINUE and ESCALATE complete the bounded choice set.
  5. Retain work and dispatch carefully. Preserve a valid current project. Switching requires a recorded human change or a validated change in need/feasibility; do not switch on every attention turn. Revalidate state and the research-plan revision before applying an action. Human game-side research changes suspend conflicting framework writes until reconciled.
  6. Verify useful progress. Track project progress and completion separately from the parent capability goal. Intermediate prerequisite projects can complete without a new building. Terminal unlocks generate bounded build, bill, equipment, or staffing tasks, and the parent goal succeeds only when the intended capability is observed in use.

Steward integration constraint: the inspected steward.research queue automatically advances to a project the game considers startable. It does not evaluate this framework’s maintenance policy, and clearing that queue does not stop the current project. Keep the long-term backlog in the framework and submit only the freshly validated project when idle; leave no pending automatic backlog. Reconcile existing queue ownership before adopting a save, and never silently clear a human-managed queue. An approved project switch needs a separate validated current-project action; replacing a Steward queue alone does not switch active research. Pausing research requires a separately validated labor/control action through the arbiter, with observed confirmation; until that capability is verified, pause the game and surface review when research must stop. Review and improvement

Display the authored rank, effective rank after prerequisites/pins, active project, planned next project, blocked reasons, start/pause checks, estimated effort, and downstream use for every research goal. 4. Two interchangeable agent API endpoints

Exactly two configured roles: planner and decision_selector. Each has its own URL, protocol adapter, authentication reference, optional model/deployment identifier, capabilities, and limits. They may use different vendors, two local services, or the same service/model with different role instructions. Planning, decomposition, and failure reflection share the Planner role. No game logic may branch on a vendor name.

“Any endpoint” means one that can satisfy the relevant contract through an adapter. Changing a compatible service is configuration-only; an unfamiliar request/response or agent-job protocol requires a new adapter. A fixed-choice service such as Jev can fill the selector role but cannot fill the planning role by configuration alone. A general model can fill either role if its outputs pass the same validation.

Adapters and protocol handling

Planned initial adapters: openai_chat_completions, anthropic_messages, typesafe_systemone, and registered custom HTTP/agent adapters. The inspected RimAgent client already uses OpenAI-compatible chat completions; its Qwen-specific options must remain adapter settings rather than mandatory fields for every provider. The Anthropic adapter handles native message/tool blocks; the TypeSafe adapter compiles the same matrix into Choice criteria. [3][17]

  • One matrix definition: option IDs, intent, criteria, exclusions, and verification live in the framework. Adapters serialize that definition for the selected protocol without inventing options or changing execution authority.
  • Structured results: use native structured output or schema-defined tool arguments where supported; otherwise parse and validate returned JSON. Never execute free text. A bounded repair attempt consumes the same deadline/budget; persistent malformed output becomes a visible failure.
  • Agent endpoints: an adapter may support session IDs, asynchronous jobs, streaming, or tool requests. Wait for a complete result within the deadline, correlate job/session state to the episode, and cancel when supported or ignore late results. Do not resubmit an uncertain job unless provider idempotency or reconciliation makes it safe.
  • Tool authority: framework-executed tool requests may read allowed observations or submit proposals. Neither remote role receives an independent game-write path. The single local dispatcher remains the authority for actions.
  • Persistent state: plans, tasks, policies, matrices, and outcomes remain in the framework’s store. Provider conversation/session history is supplementary, isolated per run, and reconstructible from framework data after a provider switch.

Capabilities, confidence, and endpoint changes

A no-game-write connection test must check more than HTTP success. Use role fixtures to check supported operations, structured output, legal option selection, abstention/refusal handling, missing confidence, response size, timeouts, and any enabled tool/session protocol. Display precise gaps, such as “returns choices but cannot produce a task graph.” Native tool calling and probability distributions are optional; a valid structured role result is required.

Confidence is optional and provider-specific. Preserve missing values as null; never invent 1.0, convert a choice into a one-hot probability distribution, or treat a model’s self-reported confidence as calibrated correctness. Tag available signals by source and evaluate them per endpoint/model/matrix. The default for unknown confidence is the rules fallback. A separately tested policy may allow schema-valid low-risk choices without a confidence gate, or route them to human review. Swapping endpoints never silently inherits the previous provider’s confidence thresholds.

Test and stage a configuration change, stop new requests using the old revision, and drain or discard outstanding results before activation at a turn boundary. Preserve task progress and reconcile existing game actions. Evaluated runs pin both endpoint configurations, adapter versions, and model/deployment revisions where available. An unversioned remote deployment is labeled unpinned; a changed endpoint starts a new evaluation configuration. Endpoint swaps must not require changes to the scheduler, matrix definitions, dispatcher, or RimWorld mods.

Routing and failure handling

  1. Calculate and filter first. Hard emergency rules override the model. Missing required facts cause an observation request or fallback. A high-confidence model answer cannot override a failed prerequisite.
  2. Batch only when the adapter supports the required semantics. Jev questions in one request independently see the same state, so a crop question cannot depend on that request’s research answer. Sequence dependent decisions and validate cross-domain resource conflicts for every provider. [5]
  3. Validate the response. Require the canonical result type, legal option IDs, matching request revisions, and acceptable age. Check finite confidence/probabilities and valid distributions only when supplied or required by the active policy. Reject malformed, refused, truncated, or stale results. Record reported model identity when available.
  4. Calibrate the active route. For Jev only, initial experimental gates could require confidence at least 0.8 and a top-two margin at least 0.2 for reversible economic choices. These are unvalidated settings, not portable thresholds. Other providers use their own tested signal gate or the explicit unknown-confidence policy.
  5. Bound network delays. Configure separate planning and decision deadlines. A two-second economic decision deadline is an initial Jev experiment; slower services need measured limits and appropriate game-speed control. Honor rate-limit guidance only within the deadline, otherwise use the configured fallback. Emergency response must never await a remote endpoint.
  6. Recheck and execute once. Use a single writer, reserve shared resources, deduplicate by decision ID and desired state, and reconcile uncertain RPC outcomes before retrying. Start with small sequences; verify postconditions and stop after partial failure.
  7. Keep the loop stable. Routine wakeups occur on relevant events and roughly every six game hours for the initial food policy. Add hysteresis and a maximum-action budget. Interrupt immediately for danger, critical shortages, stale observations, or failure; do not call either endpoint every game tick.

For live integration, preserve RimAgent’s time controls: pause or slow the game when a strategic decision needs a consistent snapshot. Measure time in both simulation ticks and wall-clock seconds. If the Planner is unavailable, continue only still-valid existing tasks and request review when replanning is essential. If the selector is unavailable, use its configured rules fallback. On prolonged outages, Steward and bounded rules continue supported play; unresolved emergencies pause and surface a clear operator event.

5. How the system improves

The framework has three loops with different authority. Execution recovery handles one failed or uncertain action: refresh state, reconcile effects, retry only when safe and justified, then block after the template’s attempt limit. Task/plan repair changes the current colony’s work when assumptions fail: choose another supported method, revise dependencies, or replan an infeasible goal. Policy learning changes reusable behavior for future decisions through a proposed diff, review, testing, and promotion. Success in the first two loops is not by itself evidence that the reusable policy improved.

Example failure case: a gathering task times out and food remains low. First determine whether the resource was unavailable, the worker was blocked, an emergency suspended work, or attention failed to revisit the task. Only then propose a scoped change such as a stalled-work review deadline or a missing access check. Stage A — learn a better policy without training a model

  1. Collect decisions and outcomes. Append immutable records with episode/start-save identity, plan/goal/task/attempt/attention IDs, observation, scheduler factors, candidates including rejected ones and reasons, model response, selected and actually executed action, fallback reason, RPC results, policy/model versions, latency, and token use.
  2. Attribute outcomes carefully. Link execution success immediately; food changes at 6 and 24 game hours; shelter at completion and the next sleep/weather interval; mood over 1–3 days; planting at harvest; research at completion; combat through incident recovery; and survival at episode end. Record intervening raids, labor changes, and policy switches. Overlapping decisions mean a food increase or mood recovery is not automatically caused by the most recent action.
  3. Diagnose failure class. Use the layer taxonomy above. Changing question wording cannot fix an unreachable stockpile, an ignored deadline, or an RPC bug. Keep factual observations separate from causal hypotheses.
  4. Propose one scoped patch. The reflection model reads development logs and returns a structured change to a planning/task template, attention rule, matrix criterion, example, threshold, or allowed parameter. Each proposal names its evidence, hypothesis, expected benefit, affected behaviors, and rejection condition.
  5. Stage instead of hot-reloading. Write candidates into a separate policy area. Freeze the active brain and policy for a scored episode. Change RimAgent’s existing mid-episode reflection path to proposal-only in this mode; disable source-changing watchdog activity during comparisons.
  6. Test and promote. Validate schema and hard constraints, run saved decision fixtures, then matched colony trials. Activate a version atomically between episodes only after its promotion gate passes. Keep the last accepted version and its manifest for rollback.

Run local recovery on demand, summarize repeated failures at a configurable game-day cadence, and propose reusable changes after an episode or a sufficient failure cluster. Keep a regression fixture for every accepted fix and compare repeated-failure frequency afterward. If a promoted change fails its monitoring gate, roll it back with its evidence intact.

Retain useful failures as well as successes. Do not train only on high-scoring runs, copy the existing chat agent as unquestionable truth, or treat the reflection model’s explanation as an observed causal fact.

Persistent lessons with context and counterevidence

Separate evidence from active policy. lessons-learned.example.yaml defines a proposed append-only ledger spanning colonies, while immutable run events retain the underlying evidence. Each lesson has a stable ID, revision, provenance, applicability and exceptions, game/mod/policy versions, map and pawn context, trace links, expected versus observed results, supporting and contradicting evidence, alternative explanations, and review state. Human corrections append a revision; contradicted and superseded lessons remain inspectable. Record successes and near misses as well as failures.

Example priors: “low available mining capacity favors feasible surface shelter” and “available skilled miners can justify secure, less flammable excavated shelter” capture the requested strategy. They are explicitly untested user priors, not discoveries from colonies we have played. lesson-records.example.yaml contains those priors and a synthetic forecast-failure hypothesis for a miner who is also the only cook; observed outcomes are null and real trial counts are zero.

Retrieve before planning and retrying. Match lessons to the current biome, terrain/roof, threat profile, effective pawn capacity, materials, deadlines, and compatible game/mod definitions. Show conflicting evidence and exclude context mismatches. A lesson's recommendation cannot override live legality, safety, or resource reservations. Persist the exact lesson revision and its effect on candidate ranking in the decision trace. Never invent outcomes for unchosen options.

Stage B — optionally train a downstream selector

After collecting enough representative actions and outcomes, train an interpretable outcome model or shallow tree ensemble. Inputs are deterministic colony features, action identity and cost, plus optional semantic judgments from the selected endpoint where they add measurable value. Outputs predict a defined outcome such as 24-hour shortage exposure or action completion. Endpoint features are an optional extension, not a required capability of every selector API.

Then rank legal candidates by expected benefit, estimated risk, and resource cost. Treat any supplied choice probabilities as model features, not success probabilities. Numeric arithmetic and final resource constraints stay in code. Compare this selector with a numeric-only model to test whether remote model features add value. Record the feature provider/version and retrain or validate when it changes.

TypeSafe’s official AutoResearch example follows a closely related pattern: a generative model proposes questions, Jev creates numeric features, and a downstream CatBoost model learns from labels. Its wine-review results demonstrate a software pattern, not proven RimWorld performance. [15]

The counterfactual problem: ordinary logs show the outcome of the action taken, not outcomes of all alternatives. Do not label unchosen options as failures. Use short, isolated branches from training saves or limited randomized choices among equally acceptable economic options to obtain comparison data. Record the real execution probability if experimenting; an endpoint’s reported distribution is not that probability. Branching runs remain separate from honest survival scores.

Stage C — constrained online adaptation, only if justified

A contextual bandit could later adapt short-horizon choices such as reserve targets. Begin with an exploration budget of at most 5% of eligible low-risk training decisions; no exploration in combat, medical emergencies, or near-starvation states. Long-delayed research, colony layout, and survival are not simple bandit problems. Full reinforcement learning is a later research option, not a prerequisite for useful self-improvement.

Autonomy boundary: validated policy parameters may improve automatically. A novel RPC template, executable tool, watcher, or mod change must pass its own code review and tests before joining the allowed action set. The learner must never improve its score by changing reward definitions, disabling failures, or altering test saves.

  1. Contracts and fixtures: assemble 100–200 varied decision cases from guide priors, real observations, and curated edge cases. Mark synthetic cases as synthetic.
  2. Interchangeability tests: use deterministic stub endpoints with different protocols to replace each role independently and both together. Assert no game writes during connection tests and no vendor assumptions in scheduling, matrices, or dispatch. Add live contract checks only for configured providers.
  3. Shadow mode: log the configured selector’s choices on baseline episodes without executing them. Review disagreement and missing options. Shadow mode measures plausibility, calibration against adjudicated decisions where available, and runtime; it cannot establish the unexecuted action’s game outcome.
  4. Short food trials: run 10-day comparisons from matched starts. Include blocked food access, cold weather, power loss, and a raid interrupting food work. Begin with roughly 6 development and 6 validation starts to find large failures, not to claim statistical superiority.
  5. Domain expansion in order: test shelter with missing beds, unfinished rooms, blocked access, and temperature-control loss; then test mood with rest/recreation deficits, room problems, and an individual pawn whose distress is hidden by the colony average. Test research next for prerequisites and labor conflicts; combat last with matched incident saves. Each stage reruns earlier-domain regression fixtures and compares the combined controller against its prior version.
  6. Full colony pilot: progress to 60-day runs, matching upstream’s default horizon. Use 12–24 matched starts and repeat selected starts to estimate variation. This is an initial budget; rare deaths and small survival differences may need many more episodes.
  7. Locked final evaluation: before tuning, reserve untouched start saves, initially at least 20. Use pilot variance to determine the final fixed sample size and minimum useful effect. Evaluate the selected frozen candidate once; if final results influence a redesign, use a new final cohort for the next claim.

Group splits and uncertainty calculations by starting save/seed family, not individual decision rows: thousands of correlated steps from one colony are not thousands of independent experiments. Use paired comparisons and confidence intervals clustered by start. Predeclare the sample size or an explicit sequential stopping procedure rather than stopping whenever a result looks favorable.

RimAgent already combines days, colonists, wealth, mood, research, raids survived, and deaths into a scalar score. Keep it as a compatibility report, but do not optimize that number alone: its positive wealth term can reward strategically harmful accumulation. [16]

Promotion rule

Before each trial, declare one primary benefit and explicit guardrail margins. A food candidate must pass all execution checks, show a meaningful paired reduction in shortage exposure, and satisfy the survival/death non-inferiority gate. For an initial conservative gate, require the 95% interval for the primary improvement to exclude zero; set the tolerated survival/death regression before seeing candidate outcomes. A small pilot with no observed deaths is not proof of equivalent safety.

If the interval is inconclusive or a guardrail fails, retain the incumbent. After promotion, an execution-contract violation disables the new policy immediately; outcome regression is assessed over a defined matched cohort before rollback. Do not automatically rewrite the matrix after every unlucky raid.

7. Implementation sequence

Keep the uploaded guide and planning material in the standalone Bvreela/BVRimAgent repository. For implementation, use a user-owned RimAgent fork pinned to upstream. Changes in the mod/ submodule belong to RimBridge first; the initial Python-only controller should avoid a bridge fork unless essential state is unavailable.

Domain roadmap: food → shelter → mood → research → combat

Food is the first complete vertical slice. Add shelter and mood next to form the initial colony-management release, then research, then combat. Every stage includes human-readable goals/tasks, bounded matrices, outcome evidence, and a failure-to-proposal example. Earlier maintenance goals remain active as new domains are added.

5. Combat: respond to threats and recoverAssess a fresh threat → choose a validated posture → execute bounded orders → monitor/preempt → rescue and recover → review the incident.Begin with shadow choices, then matched incident trials. Distinguish stale threat data, unsafe paths, wrong posture, execution failures, and uncertain incident variation before changing policy.

Rollout order is not a rigid runtime priority. The attention cycler still uses urgency, deadlines, review age, and dependencies across enabled domains. A dangerous temperature or imminent breakdown can preempt routine food work; research can progress when maintenance is covered. Deterministic emergency handling remains available from the first stage, even though the learned combat matrix comes last.

Shared-resource rule: food production, shelter construction, mood schedules, and research compete for the same labor and materials. The task manager reserves them once, explains conflicts, and routes requests to an existing task when another goal already owns the work. A mood goal caused by hunger links to food recovery instead of issuing conflicting food orders.

8. Prerequisites, costs, and the first decision

What must exist before live play

  • A licensed RimWorld 1.6 installation, Harmony, RimBridge, and Steward on a machine able to run the game.
  • Two configured endpoint roles with compatible adapters and passing capability checks. Provision credentials only where the selected services require them; pin model/deployment versions where available. Claude and Jev are optional choices.
  • A user-owned implementation fork and a small initial pack of saved starts with recorded settings.
  • Verified platform-specific build/launch paths. The inspected project documents macOS Steam paths and uses open; this research ran on Ubuntu. No compatible live installation or launch process was established.

These are implementation prerequisites, not blockers to this plan. No credentials are needed to review the design, and none were requested or used here.

Budget with measured traffic

Budget the two roles separately using their actual traffic and provider pricing. Agent services may bill per request, run, or compute time rather than tokens. Track retries and tool rounds within the request budget; do not apply one provider’s limits or prices to another.

Optional Jev pricing example: its current official model page lists $0.042 per million input tokens, free output tokens, 64k tokens per request, and 32k for the state plus the longest question. It lists 1,200 requests/minute and 250,000 tokens/second while warning that rate limits can change. Recheck the selected account’s limits and pricing before running. [4]

Illustration: at 2,000 total billed input tokens per call, 100,000 decisions would cost about $8.40 for Jev alone. One call per wall-clock second is about $0.30/hour; event-driven task decisions should usually need fewer calls. Include all questions and examples in the token estimate. Generative planning, decomposition, reflection, fallback, game compute, storage, retries, and branching trials are additional costs. These are arithmetic estimates, not measured bills.

Recommended first release: deliver food, shelter, and mood through engineering increments 1–6. First prove the full loop with food, including review and failure-driven improvement, then reuse it for shelter and mood. Each domain proceeds from recorded states through shadow mode to controlled game trials. Research and combat follow in that order.

Definition of success: humans can understand and revise what the framework is trying to do; the agent tracks work until outcomes are observed; attention returns to overdue or blocked goals; and accepted failure-driven changes improve results on unseen starts.
